## 0.13.1 — 2026-10-10

一件补齐：**时装现在也影响小头像**。上一版（0.13.0）把「一套外观」的链路与声明做了出来，但那条链只接到了
**立绘** —— 头像那一类还留在旧函数上，于是换上外观之后会出现这一幕：

> **结算页、队伍面板、手牌、商店卡上的小头像是原版，而详情页的立绘已经是新装。**

这个错**没人会报**，因为两个画面各自都对得上自己的代码。根源是引擎里同一个干员一直有**两条**互不相通的
头像解析路径（详情页那条只认 `_1` / `_2` 后缀、通用那条先精确查 `chars[id]`）—— 平时两者答案相同，
一旦引入一套外部外观就会分叉。

这一版把**每一个**头像消费点都接到同一条链上：

- `ui/gameComponents.js` 的 `UnitThumb` —— **结算页、队伍面板、手牌、商店共用这一个组件**，所以接它一次覆盖四类；
- `ui/detailPanel.js` 立绘、`ui/shopBar.js` 商店卡、`ui/fallbackField.js` 补位头像；
- `screens/{loadout,diy,ownership,support}.js` 四个屏幕。

旧的 `chessAvatarUrl` / `chessPortraitUrl` **保留导出** —— 它们是这条链的**对照实现**（链的测试逐例拿它们比对）。
另外加了两条**源码级守卫**：逐文件断言「`import` 之外没有一处还在直接调旧函数」，且「每个消费点都传了
`currentAppearanceLookup()`」。所以以后哪个消费点偷偷留着旧调用，套件会**红**，而不是给某个玩家看一张过期的图。

修好这条链还顺手换来一件事：**没有外观提供者时，上面每一处的输出与从前逐字节相同**（链的第一、二、三分支
就是旧实现那几条），所以这一版对不装外观 mod 的人**没有任何可见变化**。

上游游戏本体仍是 **0.2.2**，发行 tag：`v0.13.1-0.2.2`。这一版只发**源码包**与**升级包**两件（增量包基准 0.13.0）。

## 0.13.0 — 2026-10-10

这一版把**客户端那一层**补成可以真正写东西的样子，并把三份社区 mod 里剩下能做的那几件收口。三块内容：
**皮肤层**（外观有了一条链、一个注册面、一份包声明）、**面板能用引擎做两件小事**（记住偏好、发一条展示消息）、
**战斗倍速**作为引擎特性。上游游戏本体仍是 **0.2.2**，发行 tag：`v0.13.0-0.2.2`。

### 皮肤层：一条链、一个 hook、一份声明

皮肤（时装）是**纯外观**，所以它的分工刻意切成两半：**数据**在包里声明，**行为**在 mod 里。

- **立绘解析链统一**（`public/js/ui/portraitChain.js`，新文件）。以前同一个干员有**两条**解析路径：
  详情页 / 手牌 / 商店卡走 `chessPortraitUrl`（只认 `_1` / `_2` 后缀，别的值**静默忽略**并回落），
  而按 charId 的通用口走 `portraitUrl`（**先精确查** `chars[id]`）。没有「第三套外观」时这个差异不显形；
  一旦一个 id 既不是后缀、又不在 `chars` 里（**一套外部外观就长这样**），差异就变成「卡面是那套外观、
  详情页是原版」——**一个没人会报的错**（两个画面各自都对得上自己的代码）。现在是一条链，旧行为是它的
  **分支**而不是例外，四个消费点全部改走同一函数。测试拿今天那两个实现当**对照**逐项比对（12 条），
  唯一有意的差异（「精确命中」优先）单独钉住。
- **外观提供者**（C 层注册面）。面板模块可以（不是必须）导出 `appearance(ctx)` 返回
  `{ lookup(kind, charId, id) }`，注册点在 import 之后、**mount 之前**把它接进那条链 —— 首帧就是对的，
  不会「先画原版、下一帧跳过去」。进程内**最多一个**提供者（后注册者点名 `CLIENT_APPEARANCE_TAKEN`：
  「谁提供外观」不能取决于加载次序）；抛异常、形状不对各自点名；`dispose()` 一并收回，
  链回到「没有 hook」那条**与今天逐字相同**的路径。
- **`pack.json.skins` 声明**。顶层键新增 `skins`（它曾经在「不认识的键」名单里 —— 0.10.0 时代
  `variants` / `skins` / `i18n` 三个键被**静默丢掉**，作者写了等于没写）。形状
  `[{ id, charId, name, series?, desc?, art?, voices? }]`，其中 `art` 与官方的 `art.chars` **完全同形**，
  所以复用同一个解析器（字段白名单 / 路径必须包内相对 / spine 要齐 `skel`+`atlas` 这些判据**不出现第二份实现**）。
  新拒绝码 `SKIN_BAD_SHAPE` / `SKIN_BAD_ID` / `SKIN_BAD_CHAR_ID` / `SKIN_DUPLICATE_ID` / `SKIN_UNKNOWN_FIELD` /
  `SKIN_PATH_UNSAFE`；只带时装**算贡献项**（不再 `EMPTY_PACK`）。
- **`assets.skins[charId]` 合并**。形状是**按干员分组的一列**（`[{ pack, id, name, series?, desc?, art?, voices? }]`），
  因为客户端要问的问题永远是「这个干员有哪几套」。三条规则与既有素材通道**逐字相同**：路径转
  `/workshop-assets/…` 绝对 URL、同一个 `(charId, id)` 冲突时按**包 id 升序第一个赢**并点名
  `SKIN_COLLISION`（指出是谁占住了）、清单不在时 `MANIFEST_MISSING`。**不同干员、同一干员的不同套互不冲突**
  —— 这正是它必须单独一个函数、而不是复用 `art` 那套的原因。

### 面板能用引擎做两件小事

以前一个面板**只能看和画**：它拿不到 store、不能记偏好、也不能主动发一条消息。这挡住了插件包两件真实需求
（记住「这个干员选了哪套」、换完装**让别人也看到**）。补了两格，都刻意很窄：

- **`ctx.session.setPref` / `getPref`** —— 一格**受限偏好**：键 ≤ 64 字符、值只收 `string` / `number` /
  `boolean` / `null`，键按 `<包 id>/` 前缀分区（两个包用同一个键名不会**跨包串味**）。越界点名拒绝。
  **不是**把 store 交出去 —— store 里放着对局状态，一个面板能写它就等于能改对局。
- **`ctx.session.send(type, fields)`** —— **闭枚举** `PANEL_SEND_TYPES`，今天只有 `room.appearance`。
  形状发出前先过一遍与服务端**同一份** `validateC2S`：判不过就**不发**并点名，而不是发出去等一个 error 帧回来。
  加一条要同时改这张表、那条消息的形状、以及一条测试 —— 这是**有意的摩擦**：面板能改对局状态的那一天，
  就是这一层失效的那一天。

### `room.appearance`：换装与头像对同房的人可见

新 C2S（`{ picks?, avatar? }`），纯**展示**消息：不进 golden、不影响任何服务端判定，因此与 `combat` 无关。

- 两个字段**刻意分开**，因为归属不同：`picks` 是**按干员**的换装（`{ [charId]: { skinId } | { avatar } }`），
  `avatar` 是**玩家自己**那张头像（不按干员分组）。把头像混进 `picks` 会需要一个假的 charId 当键 ——
  那是把「人的选择」硬塞进「干员的选择」，下一个读的人必然误用。
- 两个字段都可选但**不能都不给**；浅合并（**换头像不清皮肤**，反之亦然）。每一项必须是 `{ skinId }` 或
  `{ avatar }` **恰好一个**（「两个都给」是坏消息，不是「取其一」）。
- **服务端不判定内容**：形状这一层卡死，但「这个 skinId 到底存不存在」要看包声明的 `assets.skins`，
  而**服务端看不见包内容** —— 所以它只转发，不认识的那一项由**画的一方**回落原版（可见、可解释，
  不会串到别的干员身上）。
- **比赛中也接受**（不像 `room.diy` / `room.ownership` 要等下一局）：它只改显示、不碰战果。
  变更即广播 —— 外观是**给别人看的**，必须立刻到达同房的人。
- 为「字段之间有关联」的形状给 C2S 表加了 `$check`（按字段的判据表达不了「不能都不给」，拆开就会留下那条缝）。

### 战斗倍速（引擎特性）

顶栏多了 ×1 / ×2 / ×3 / ×4 循环的倍速按钮。它是**纯本地播放选择** —— 这一条由代码保证，而不是靠约定：
`runner.setRate` 只把倍速乘进 **「墙钟 → tick」的映射**，**不改 tick 序列**，所以同一场战斗无论按到几倍，
跑过的 tick 与每一步判定完全相同，只是**跑得快慢**不同。测试钉住的是那句话本身：4× / 1× / 0.5× 分别跑完
同一场，**tick 数与 `b.result` 逐字节相同**。服务端在 `b.start` 里给的 `speed` 是**对局**节奏，
一个字节都不动 —— 玩家改的是**这台机器看得多快**，两者相乘。

### `ctx.me`：一格只读会话态

面板答不出来、只能由引擎告知的事实：`playerId` / `name` / `room`（展示面快照：`code` / `mode` /
`difficulty` / `inMatch` / `mySeat` / `spectating` / `mods`），外加 `snapshot()` 一次取全。
它是**活读数**（面板挂上后不重挂，一次性的值会变陈旧 ⇒ 每次读都取当前值，与 `ctx.data.get()` 同一条思路），
返回对象**冻结**，而**没有** store 句柄 / `match` / `battle` / `battleRunner` / `audio`。
刻意**不含** `search`（野排匹配态）：那个读数活在房间屏自己的 `useState` 里，把它提升进 store 是**另一件事**。

### 两处宿主键

- `screen.loadout.detail` 的宿主以前只有 `data-mod-slot`、**没有** `data-mod-slot-key` ⇒ 挂在这里的面板
  `ctx.hostKey` 永远是 `null`，**答不出「当前是哪个干员」**（皮肤选择器只能画空态）。补上那一个属性，
  并把属性名提成 `SLOT_KEY_ATTR` 一份真相（注册点 / `hostKeyOf` / 渲染宿主的引擎组件共用）。
- `game.hud.topBar` 之外，`CLIENT_WRAP_COMPONENTS` 的四个具名组件不变。

### 三份社区 mod 的迁移进度

- **插件包**：`skinPicker` 从「只能画空态」变成**真能画**（官方内置皮肤与包声明的时装合成**一条链**、

  那一项」这条接口边界）。
- **fanpack**：它的两个新客户端屏幕早已按 C 层落地，本版给它接上了上面这两格（换装节、宿主键）。
- 第三方 mod 仍**保持为 mod**：不进发行版、不发 release、不改 `data/*.json`。

### 上游更新的校对清单

新增 `docs/UPSTREAM-UPGRADE.md`：原项目发新版时照它走一遍，就能找齐所有会被上游改动打断的地方。
一句话结论：**上游挪文件时只改白名单里那一行别名，包不动、已装的 mod 不重置** —— 实测（把 `tier2.js` 改名）
守卫在 CI 期就报缺失，用到它的包得到 `KIT_IMPORT_FAILED` 并**点名是哪个包的哪个 kit**，重指之后同一个包原样能跑。
只有「契约语义真的变了、没有别名可对」才抬 `MOD_API_VERSION`，那时老包会**响亮地被拒**（这是我们要的，
不能悄悄跑错）。**加一格能力永远不抬版本**，所以这一版新增的表面都是**加法**，已发布的包不会被拒。
